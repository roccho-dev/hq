# Official hq artifact lineage

## Purpose

Keep one reconstructible product lineage for `hq` and `hq-worker` across Linux and native Windows.

This document identifies artifact authority. It does not define environment placement, profile activation, worker supervision, world authoring, command meaning, or result meaning.

```text
exact hq proposals commit
  -> one clean official producer
  -> four platform binaries
  -> platform manifests
  -> one product manifest and SHA256SUMS
  -> immutable commit-tagged release
  -> complete release readback
  -> exact envs placement and activation
```

## Authority map

| Concern | Authority |
|---|---|
| product source | one exact commit on `roccho-dev/hq@proposals` |
| official producer | `.github/workflows/official-hq-proof.yml` at that commit |
| immutable release | `hq-artifact-<full source SHA>` |
| artifact bytes | the release assets named by `SHA256SUMS` |
| platform metadata | `manifest-linux-amd64.json` and `manifest-windows-amd64.json` |
| product family metadata | `hq-product-manifest.json` |
| complete publication readback | successful `.github/workflows/verify-official-release.yml` and tag `hq-artifact-verified-<full source SHA>` |
| placement, binding, profile activation, and supervision | `roccho-dev/envs` using exact release asset digests |

The verified tag is evidence that the complete release was downloaded and checked. It is not a second artifact authority and must point to the same source commit as the release target.

## Official binary family

Exactly four binaries form one official product family:

| OS | Binary |
|---|---|
| Linux amd64 | `hq-linux-amd64` |
| Linux amd64 | `hq-worker-linux-amd64` |
| Windows amd64 | `hq-windows-amd64.exe` |
| Windows amd64 | `hq-worker-windows-amd64.exe` |

Other workflow binaries, local builds, merge-ref artifacts, test helpers, and historical proof packages are evidence only. They are not valid placement inputs for an active production profile.

## Producer invariants

For each supported platform, the official producer must:

1. check out one exact source revision;
2. use exact Go `1.23.12`;
3. require a clean source tree before building;
4. build both binaries outside the repository before any test can modify the tree;
5. require the repository to remain clean after both builds;
6. embed the exact checkout revision in both binaries;
7. positively prove `vcs.modified=false` for both binaries;
8. reject either binary when `vcs.modified=true` or the embedded revision differs;
9. record binary SHA-256 values in the platform manifest;
10. run product proofs against the already-built official `hq` binary rather than rebuilding a substitute.

Linux and Windows artifacts may differ because they target different operating systems. Within each target, there is one official `hq` and one official `hq-worker` generated by the same platform job from the same source commit and toolchain contract.

## Release and verification contract

A valid release has the exact tag:

```text
hq-artifact-<full source SHA>
```

Its authoritative `SHA256SUMS` lists exactly these seven files:

```text
hq-linux-amd64
hq-worker-linux-amd64
hq-windows-amd64.exe
hq-worker-windows-amd64.exe
manifest-linux-amd64.json
manifest-windows-amd64.json
hq-product-manifest.json
```

The release verifier must:

1. select only the release for the current exact `proposals` SHA;
2. download `SHA256SUMS` from that release;
3. reject unknown or unsafe authoritative filenames;
4. download every listed authoritative file from that same release;
5. require exactly seven checksum rows;
6. run `sha256sum -c` over all seven files;
7. require both platform manifests to identify the exact source SHA and Go `1.23.12`;
8. require the product manifest to identify two builds and exactly the four official binaries;
9. create `hq-artifact-verified-<full source SHA>` only after all checks pass;
10. never move an existing verified tag to another commit.

A release tag without the verified tag is not sufficient closure evidence. A verified tag without an exact matching release and checksums is invalid by construction.

## Downstream consumption

`envs` must consume:

- the exact source SHA;
- the exact immutable release tag;
- the exact platform binary names;
- the exact binary SHA-256 values from the release manifests;
- the required hq binding contract and deployment identity.

`envs` must not:

- rebuild hq as an independent product authority;
- consume expiring pull-request proof artifacts as production inputs;
- select a mutable latest release;
- choose a binary by PATH, shell profile, current directory, or filename search;
- reinterpret hq world, queue, worker, provider, or result semantics.

The active profile must resolve one exact `hq` and one exact `hq-worker` appropriate for its target OS, and activation evidence must link those bytes to the release and source revision.

## Reconstruction procedure

A third party can reconstruct the producer handoff as follows:

1. identify the exact accepted `proposals` commit;
2. resolve `hq-artifact-<source SHA>` and require its target to equal that commit;
3. resolve `hq-artifact-verified-<source SHA>` and require it to equal the same commit;
4. download `SHA256SUMS` and the seven authoritative assets;
5. run `sha256sum -c SHA256SUMS`;
6. verify both platform manifests and `hq-product-manifest.json`;
7. inspect each selected binary's embedded VCS revision and clean-tree evidence where required;
8. follow the exact binary digest into the envs binding, deployment, active profile, runtime world observation, run, and result evidence.

No local worktree, pull-request merge ref, workflow cache, terminal transcript, or expiring artifact is required as authority.

## Rejected false green

During PR #133, an initially green proof artifact was downloaded and rejected because both platform `hq-worker` binaries reported `vcs.modified=true`.

The first binary had been written inside the repository before the second build, making the second build dirty. The initial rejection pattern also failed to match the actual `vcs.modified=true` build-info form.

That run remains historical negative evidence. It is not an official artifact and must never be used as a downstream placement input. The accepted producer builds outside the repository and positively requires `vcs.modified=false` for both binaries.

## Ownership boundary

| Repository | Owns | Must not own |
|---|---|---|
| `hq` | product source, official producer, manifests, immutable release, release readback | target placement, profile activation, service layout |
| `envs` | exact target selection, verified binding, placement, activation, supervision, deployment evidence | hq source, queue meaning, worker semantics, canonical result meaning |
| `edits` | Vim client integration and user-visible conformance | hq artifact production or target placement |
| `adrs` | accepted architecture and closure evidence map | generated artifact bytes or runtime state |
