# Run status taxonomy v1

## Statuses

| status | terminal | meaning |
|---|---:|---|
| `queued` | no | Instruction accepted; adapter not started. |
| `running` | no | Adapter started and may emit output. |
| `completed` | yes | Run finished successfully. |
| `failed` | yes | Adapter or worker failed. |
| `blocked` | yes | Validation, policy, or precondition denied execution. |
| `timeout` | yes | Bounded runtime expired. |
| `cancelled` | yes | Cancellation was accepted before completion. |

## Allowed transitions

```text
queued  -> running | blocked | cancelled
running -> completed | failed | blocked | timeout | cancelled
```

Terminal statuses have no outgoing transition. Unknown statuses fail validation.

`stdout` and `stderr` result events do not change status; they are valid only while status is `running`.

## Event mapping

| result kind | status effect |
|---|---|
| `accepted` | set `queued` |
| `started` | `queued -> running` |
| `stdout`, `stderr` | keep `running` |
| `completed` | `running -> completed` |
| `failed` | `running -> failed` |
| `blocked` | `queued|running -> blocked` |
| `timeout` | `running -> timeout` |
| `cancelled` | `queued|running -> cancelled` |

## Retry

There is no `retrying` status and no terminal-to-queued transition. A retry is a new instruction/run linked with `reply_to`.
